# AOF v10.2 Release Definition

## Release Theme

External Provider Integration Pilot Selection.

v10.2 does not connect to or execute against a real external provider. It selects the first provider pilot candidate and defines why that provider is the correct next bounded experiment after the v10.1 third-party validation contract.

Human-facing wording:

> v10.2 tells an operator which external provider pilot AOF should try first, why that pilot is selected, what alternatives were rejected, and what must remain blocked before real integration or live execution.

## What Users Can Do Now

After v10.2, a user can:

- see the first external provider pilot candidate and selection rationale
- distinguish provider pilot selection from provider integration or execution
- inspect alternatives and rejection reasons before work starts
- require validation, approval, cost, rollback, and incident gates before any live provider action
- block stronger product claims until the selected pilot is actually integrated and validated

## Capability Delta

NEW:

- `PCAP-EXTERNAL-PROVIDER-PILOT-SELECTION`: AOF can choose a bounded first provider pilot candidate with rationale, alternatives, and blocked conditions.

UPDATED:

- `PCAP-THIRD-PARTY-VALIDATION-CONTRACT`: validation contract now feeds provider pilot selection criteria.
- `PCAP-EXTERNAL-RUNTIME-PRODUCTIZATION`: productization now has a concrete provider pilot frontier.
- `PCAP-PRODUCTION-READINESS-REVIEW`: readiness remains blocked until provider pilot evidence exists.

REMOVED:

- None.

## Selected Pilot Candidate

The selected first pilot candidate is a read-first GitHub provider pilot.

Selection rationale:

- GitHub is already the release, CI, issue, tag, and release-note coordination surface for AOF.
- The first pilot can start read-only and therefore avoids premature external writes.
- AOF already has strong release-state, CI, tag, and release evidence to compare against provider observations.
- The pilot can later graduate to write actions only after approval, rollback, incident, cost, and third-party validation gates are satisfied.

Rejected or deferred alternatives:

- Slack: useful for operator feedback, but weaker as a first lifecycle proof surface.
- Jira: useful for work tracking, but not the current canonical AOF release surface.
- OpenAI/provider execution: too close to live execution authority before provider read integration is validated.
- npm publish: irreversible/product-distribution risk is too high for first pilot.

## Not Proven Boundary

v10.2 does not prove:

- completed external provider integration
- live provider execution
- provider write authorization
- production safety
- third-party validation completion
- market value or external adoption

## Release Decision

Release only if AOF makes it harder to confuse:

- provider pilot selection with provider integration
- read-only pilot planning with external write permission
- GitHub provider candidate with general provider support
- structural audit pass with real provider behavior
