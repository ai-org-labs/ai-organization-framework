# AOF v9.7 Archmap v0.4.0 Adoption

## Purpose

Archmap `v0.4.0` is now the AOF architecture-map provider baseline.

The important change is not visual polish. The important change is that Archmap now has a plugin-first lifecycle foundation that can represent:

- Requirement
- Acceptance Criterion
- Decision
- Risk
- Test
- Evidence
- typed lifecycle relations
- Requirements / Traceability / Quality projection views
- deterministic graph trace APIs
- DSL-authored Runtime views

AOF already stores those concepts as governed artifacts. v9.7 aligns the AOF Archmap contract so those artifacts can be projected into Archmap lifecycle views without making Mission Control or Archmap the source of truth.

## External Provider Baseline

- Archmap: `https://github.com/ai-org-labs/archmap/releases/tag/v0.4.0`
- Local external reference: `.aof/external-refs/Archmap-v0.4.0.json`
- Optional icons remain external via `@archmap/icons`.

## AOF Mapping

| AOF artifact family | Archmap v0.4 lifecycle concept | AOF source of truth |
|---|---|---|
| Need / Project / Work Item | Requirement | `.aof/tasks/**`, release definitions |
| Project readiness / acceptance gates | Acceptance Criterion | `.aof/artifacts/work-readiness/**`, release checklists |
| ADR / Council review | Decision | `.aof/decisions/**`, `.aof/artifacts/execution/council-reviews/**` |
| Risk candidates / blockers / not-proven boundaries | Risk | session exports, product value evidence, release definitions |
| `npm test`, smoke, audits | Test | test logs, audit artifacts, release-state audit |
| runtime records / coverage / session exports | Evidence | `.aof/artifacts/**` |
| Archmap impact record | Architecture lifecycle trace | `.aof/artifacts/archmap/impact/**` |

## Runtime Boundary

AOF does not vendor Archmap v0.4.0.

AOF uses Archmap v0.4.0 as an external provider baseline. The AOF runtime remains responsible for:

- writing canonical AOF artifacts
- validating AOF artifact references
- deciding whether work is release-ready
- preserving not-proven boundaries
- projecting architecture and lifecycle state into Mission Control

Archmap remains responsible for:

- semantic graph representation
- rendering
- extension/plugin APIs
- lifecycle projection views when explicitly used by a governed work item

## Mission Control Implication

Mission Control should be able to show architecture and lifecycle traceability, but it must not become the source of truth.

The source of truth remains:

- AOF runtime artifacts
- Archmap source files
- Council review artifacts
- verification artifacts
- release-state audit evidence

## Acceptance Gate

The adoption is complete only if:

- AOF docs name Archmap `v0.4.0` as the current provider baseline.
- AOF records a local external reference artifact for Archmap `v0.4.0`.
- `docs/archmaps/aof-runtime-current.archmap` includes lifecycle traceability nodes or metadata for Requirement, Acceptance, Decision, Risk, Test, and Evidence.
- The Archmap integration doc states that lifecycle views are opt-in provider capabilities, not automatic AOF proof.
- `archmap-impact-audit` and `release-state-audit` remain green.

## Not Proven

This adoption does not prove:

- third-party operator comprehension
- rendered view usability
- external Archmap package availability in every user environment
- semantic correctness of every lifecycle relation
- production provider execution safety

It only establishes the governed AOF-to-Archmap lifecycle traceability baseline.
